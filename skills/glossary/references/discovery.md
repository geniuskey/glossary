# 용어집 기반 새 도전 발굴

조직의 지식이 용어·관계·위키로 정리되어 있으면, 그 **구조의 빈틈**에서 사람이 아직 잇지 않은 조합을 찾을 수 있다. 이 문서는 에이전트가 용어집을 근거로 새 도전 가설을 만들고 스스로 검증하는 절차다. "새로운 기회", "아무도 시도하지 않은", "숨은 연결", "혁신 과제" 같은 요청에 읽는다.

핵심 원칙: **새로움은 구조에서, 의미는 정의에서, 판단은 사람에게.** 일반 지식으로 그럴듯한 전략을 지어내지 않는다. 모든 추론 단계는 용어 정의나 그래프 신호를 인용한다.

## 1. 재료 모으기 (read scope)

1. 구조 신호: `GET /discovery?limit=30`. AI를 쓰지 않는 결정적 계산이다. 도메인을 좁히려면 `GET /discovery?domain=<key>`, 한 종류만 보려면 `GET /discovery?kind=latent_link`.
   - `latent_link`: 공통 이웃·위키 동시 언급·임베딩 유사도는 있는데 승인된 관계가 없는 용어 쌍. **새 도전의 주 재료.** `metrics.crossDomain=1`이고 `metrics.sharedPages=0`이면 가장 새롭다.
   - `bridge`: 여러 도메인을 잇는 용어. 한 도메인의 해법을 다른 도메인으로 옮기는 통로.
   - `silo`: 각자 용어는 많은데 서로 관계가 거의 없는 도메인 쌍. 조직의 단절.
   - `implied`: 추이 관계(`is_a`, `part_of`)가 함의하지만 기록되지 않은 관계. 정리 과제이자 숨은 가정.
   - `knowledge_debt`: 많이 기대지만 정의가 얕은 용어. 여기에 기대는 가설은 먼저 정의를 확인한다.
   - `score`는 같은 kind 안에서만 비교한다. `novelty`(0~1)는 kind를 넘어 비교할 수 있다.
2. 정의와 표기: `GET /terms/catalog` 한 번으로 전체 용어의 정의·표기·`revision`을 받는다. 신호에 나온 용어만 필요하면 `GET /terms/{idOrSlug}`.
3. 이미 아는 것: `GET /wiki?q=<용어>`로 해당 조합을 이미 다룬 공개 문서가 있는지, `GET /relations?termId=<id>`로 기존 관계를 확인한다. 이미 다룬 조합은 "새 도전"이 아니라 "실행 과제"다.

사내 모델로 빠르게 1차 결과를 보고 싶으면 `POST /discovery` 본문 `{"focus":"<주제>","maxIdeas":5}`. 가설·추론 단계·비평 점수를 돌려준다(10분에 6회). 더 깊은 추론은 아래 절차를 직접 수행한다.

## 2. 가설 만들기

신호 하나마다 아래 연산자 중 맞는 것을 적용한다. 한 가설은 **서로 다른 개념의 용어를 둘 이상** 결합해야 한다.

| 연산자 | 질문 | 잘 맞는 신호 |
|---|---|---|
| 전이 | A 도메인에서 문제를 푼 메커니즘을 B 도메인의 비슷한 제약에 옮기면? | latent_link(교차 도메인), bridge |
| 유추 | A와 B가 같은 이웃을 공유한다면, A에 성립하는 무엇이 B에도 성립하는가? | latent_link(공통 이웃) |
| 결합 | 단절된 두 도메인의 자산을 합치면 어느 쪽도 혼자 못 하는 무엇이 가능한가? | silo |
| 역발상 | 정의에 적힌 제약·전제를 뒤집으면 무엇이 열리는가? | knowledge_debt, implied |
| 함의 추적 | 기록되지 않은 A→C가 참이라면 지금 운영에서 무엇이 달라져야 하는가? | implied |

각 가설은 다음을 갖춘다.

- **가설**: 한두 문장. "X의 Y를 Z에 적용하면 W가 개선된다" 꼴로 검증 가능하게.
- **추론 단계**: 정의(용어 slug·revision)와 신호를 인용하며 가설에 이르는 3~6단계. 정의에 없는 사실은 `가정:`으로 시작한다.
- **왜 아직 아무도 하지 않았나**: 관계 부재, 사일로, 정의 공백 등 구조 근거로 설명한다. 업계에 널리 알려진 아이디어면 버린다.
- **첫 실험**: 2~4주 안에 작게 검증할 구체적 실험과 관찰 가능한 성공 지표.
- **위험과 전문가에게 물을 질문**.

## 3. 스스로 반박하기

가설마다 다른 관점으로 한 번 더 읽고 1~5점으로 채점한다. 근거성이 가장 중요하다.

- 근거성: 추론 단계가 정의·신호로 실제 뒷받침되는가? 가정 표시 없이 단정한 사실이 있으면 2점 이하.
- 새로움: 인용 용어끼리 이미 관계나 같은 공개 위키로 이어져 있지 않은가? 이어져 있으면 감점한다.
- 실현성: 첫 실험이 작고 구체적인가?
- 영향: 성공하면 조직에 의미 있는 변화가 있는가?

살아남은 가설은 가장 약한 고리를 검색어로 용어집 전체(`GET /terms?q=`, `POST /rag/search`, `GET /wiki?q=`)를 다시 찾아 뒷받침·반박·근거 부족을 판정하고 인용을 붙인다. 근거 없이 "확인됨"이라고 쓰지 않는다.

근거성 2점 이하 또는 진부한 가설은 버리고, 버린 개수도 보고한다. 서로 다른 도메인의 동음이의어를 같은 개념으로 묶지 않았는지 반드시 확인한다(`homonyms`).

## 4. 결과 남기기

- 사용자에게는 점수 순으로 가설·근거 용어 링크(`{GLOSSARY_URL}/g/{slug}`)·첫 실험·불확실성을 보고한다. 가설은 **추론이지 검증된 사실이 아님**을 밝힌다.
- 사용자가 원하면 가설을 위키 초안으로 남긴다: `POST /wiki` 본문에 `title`, `content`(가설·추론·실험 계획), `termSlugs`(인용 용어). 초안은 공식 근거가 아니므로 공개는 사람이 검토한다.
- 가설을 용어 정의(`definitionMd`)에 쓰지 않는다. 발굴 중 발견한 정의 공백·함의 관계는 별도 정리 제안으로 분리한다(`references/curation.md`).
- 발굴 품질은 그래프 품질을 넘지 못한다. 신호가 거의 없으면 가설을 짜내지 말고, 관계·정의를 보강할 지점(knowledge_debt, implied)을 먼저 제안한다.

## 5. 그래프를 두껍게 하는 순환

발굴 → 관계 제안 → 사람 승인 → 다음 발굴이 더 많은 구조를 본다. 이 순환이 용어집을 "사전"에서 "추론할 수 있는 지식"으로 바꾼다.

- `POST /discovery/relations` 본문 `{"dryRun":true}`로 함의된 관계(A→B→C의 A→C)와 근거가 강한 숨은 연결을 관계 제안 후보로 미리 본다. 이미 관계 행이 있는 쌍은 거절된 것까지 제외된다.
- 저장(`dryRun:false`)은 로그인 세션 또는 write API 키로 한다. 저장해도 `proposed` 상태일 뿐이며 승인은 사람이 관계 검토에서 한다. 저장 전에 미리보기 목록을 사용자에게 보여 준다.
- 개념 용어 전체의 관계는 `POST /discovery/relations/curate`로 페이지 단위로 정리한다. 절차와 완료 기준은 `references/organize.md` 4절.
- `knowledge_debt` 신호의 용어는 정의 보강 후보로 `references/curation.md` 루틴에 넘긴다.
