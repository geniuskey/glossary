# 조직 지식을 용어집으로 정리하기 (전체 순서)

"우리 용어집 전체를 정리해줘", "이 용어집으로 추론할 수 있게 만들어줘"처럼 용어집 **전체**를 다루는 요청에 읽는다. 개별 루틴은 `references/curation.md`, 발굴은 `references/discovery.md`에 있다. 이 문서는 그 루틴을 **어떤 순서로, 언제까지** 돌릴지 정한다.

왜 순서가 중요한가: 발굴과 챗봇 답변의 품질은 **관계와 정의의 밀도**를 넘지 못한다. 실데이터에서 용어 1,545개에 승인 관계가 13개뿐이었을 때, 발굴 가설은 모두 "용어집 근거 부족"으로 판정됐다. 용어 수를 늘리는 것보다 **정의를 채우고 관계를 잇는 것**이 먼저다.

모든 쓰기는 **미리보기 → 사용자 확인 → 저장 → 재조회** 순서다. 한 번에 처리한 건수와 남은 건수를 단계마다 보고한다.

## 0. 시작 전 확인 (사람이 할 일 포함)

- `GET /api/v1/health`, `GET /api/v1/openapi`로 배포 버전에 `/discovery`, `/discovery/relations/curate`가 있는지 확인한다. 없으면 서버 업그레이드가 필요하다고 보고하고 해당 단계를 건너뛴다.
- API 키 scope: 조회 `read`, 저장 `write`. 둘 다 필요하다.
- 서버 AI 연결과 **RAG 임베딩 색인**은 관리자가 화면에서 켠다. `POST /discovery/relations/curate`가 503 `ai_not_enabled`이면 AI가 꺼진 것이고, 모든 용어의 `candidates`가 0이면 임베딩 색인이 없는 것이다. 둘 다 사용자에게 요청한다.

## 1. 현황 진단

1. `GET /discovery?limit=20` — `stats`(용어·관계·공개 위키·의미 이웃 수)와 신호를 본다.
2. 아래 표를 만들어 보고한다. 이것이 정리의 출발점이자 완료 판단의 기준이다.

| 지표 | 계산 | 목표(권장) |
|---|---|---|
| 관계 밀도 | `stats.relations / stats.terms` | 개념 용어당 1개 이상 |
| 지식 부채 | `kind=knowledge_debt` 신호 수 | 0에 가깝게 |
| 사일로 | `kind=silo` 신호 중 `metrics.crossRelations=0` | 줄어드는 추세 |
| 공개 위키 | `stats.wikiPages` | 주요 업무 절차마다 1건 |

## 2. 중복·표기 정리 (`curation.md` 2절)

같은 개념이 둘로 나뉘어 있으면 관계가 두 곳에 흩어진다. 관계를 잇기 전에 먼저 한다.

- `GET /contributions/duplicates?status=pending`부터 처리한다. 병합은 사용자 확인 후에만 한다.
- `GET /discovery?kind=latent_link`에서 `metrics.nearDuplicate=1`인 쌍(의미 유사도 0.93 이상)도 중복 후보다. 제품 모델 파생형(IMX381·IMX318)은 대개 다른 제품이므로 병합하지 말고 `different`로 기록한다.
- 완료 기준: 대기 중복 후보 0건, 또는 남은 건이 전부 사람 결정 대기.

## 3. 정의 보강 (`curation.md` 1·3절)

관계 정리 에이전트는 **정의를 비교해** 관계를 고른다. 정의가 비면 관계도 못 찾는다.

- 우선순위: `kind=knowledge_debt` 신호의 용어(많이 쓰이는데 정의가 얕음) → 본문은 있는데 정의가 빈 용어(`GET /contributions/term-definitions`) → 미분류 용어.
- 정의는 본문·원문 근거로만 쓴다. 일반 지식으로 지어내지 않는다.
- 완료 기준: 지식 부채 신호의 용어에 모두 40자 이상의 근거 있는 정의.

## 4. 관계 정리

두 가지를 순서대로 돌린다. 둘 다 **proposed로만 저장**되고 승인은 사람이 관계 검토 화면에서 한다. 상태와 무관하게 이미 관계 행이 있는 쌍(거절 포함)은 다시 제안하지 않는다.

1. **함의 관계**: `POST /discovery/relations` `{"dryRun":true}` → 사용자에게 목록 확인 → `{"dryRun":false}`. 추이 관계(A part_of B, B part_of C → A part_of C)라서 정확도가 높다.
2. **개념 용어 관계**: `POST /discovery/relations/curate`를 페이지 단위로 부른다.

   ```json
   {"offset":0,"limit":10,"dryRun":true}
   ```

   - 응답의 `relations`를 사용자에게 보여 주고, 확인되면 같은 범위를 `"dryRun":false`로 다시 부른다. 다음 범위는 `nextOffset`으로 이어 간다(`null`이면 끝).
   - 요청당 10개, 용어마다 모델 호출 1회라 느리다. 한 시간 30회 제한이 있으니 큰 용어집은 여러 번에 나눠 진행하고 진행률(`offset / total`)을 보고한다.
   - 특정 용어만 다시 보려면 `{"termSlugs":["etching","etch-bias"]}`.
   - 판정 검토 팁(실데이터에서 관찰): `related_to`가 가장 많고, `is_a`를 과업↔방법 관계에 잘못 쓰는 경우가 있다(예: Classification is_a Supervised Learning → `used_in`이 맞다). 사용자에게 넘길 때 종류가 의심스러운 항목을 표시한다.
3. 직접 찾은 관계는 `POST /relations`로 하나씩 제안한다. 양쪽 용어의 현재 리비전과 근거(`evidenceMd`)가 필요하다.
4. 완료 기준: 개념 용어 전체를 한 번 순회했고, 남은 제안이 전부 사람 승인 대기.

승인은 대신하지 않는다. 승인 대기 건수와 "먼저 검토하면 좋은 관계"(신뢰도 높은 is_a·part_of, 사일로를 잇는 관계)를 정리해 사용자에게 넘긴다.

## 5. 발굴 (`references/discovery.md`)

관계가 승인된 뒤에 돌린다. 승인 전 proposed 관계는 그래프에 들어가지 않으므로 발굴 결과가 바뀌지 않는다.

- `POST /discovery` `{"maxIdeas":5}` 또는 주제를 주어 `{"focus":"센서 신뢰성"}`.
- 가설마다 근거 용어, 비평 점수, 용어집 검증 결과(`verification.verdict`)를 보여 준다. `insufficient`는 "용어집에 그 인과 지식이 없다"는 뜻이다. 무엇을 확인하면 되는지(`verification.query`)와 함께 보고한다. 그 확인 결과가 다음 정리 단계의 입력이다.

## 6. 기록

- 사용자가 고른 가설만 위키 초안으로 저장한다(`POST /wiki`, `status` 생략 = draft). 본문에 가설·추론·첫 실험과 빈 "실험 결과" 칸을 둔다. 공개는 사람이 한다.
- 실험 결과가 위키에 적혀 공개되면, 그 인과 지식이 다음 발굴과 챗봇 답변의 근거가 된다. 이 순환이 한 바퀴 돌아야 용어집이 "사전"에서 "추론할 수 있는 지식"이 된다.
